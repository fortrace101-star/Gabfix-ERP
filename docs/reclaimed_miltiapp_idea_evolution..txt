4. Sync protocol (the core design)
Write path — always local-first:

Online: write Dexie (pending) → immediate push() → server ACK → mark synced, store serverId + authoritative number/PDF URL. UI shows optimistic state with "Syncing…" then "Synced".
Offline: write Dexie (pending) → outbox row → UI shows "Waiting to sync (N)". No blocking; counter keeps serving customers.
Push: POST /api/sync/push (new, enhance.md §9 addition) accepts ordered ops with idempotency_key. Server applies idempotently (retries safe), returns per-op { localId → serverId, number, status, server_updated_at }. Auth: same JWT + requireScope('laundry'); expired token → queue stays, UI prompts re-login, no data loss.

Pull: GET /api/sync/pull?branch_id&since=<last_pull_at> returns delta (orders/items/payments/methods/pricelist changed by others, e.g. Admin edits). Client upserts into Dexie, advances last_pull_at. First login does a bounded seed pull (this branch, last 90 days + open orders).

Temp-ID reconciliation (resolves the document_sequences conflict):

Offline orders/payments carry local-<uuid> + idempotency_key. Server assigns the real number (LND-…, RCPT-…) at push time from document_sequences — numbers are therefore never assigned offline, only mapped on ACK. Ticket printed offline shows DRAFT local-… / amounts; reprint after sync shows the authoritative number. This preserves enhance.md §8 uniqueness without distributed counters.
All FK references inside one push batch resolve by idempotency_key, so an order + its items + its payment created offline in one session link correctly server-side.
Conflict policy (server-wins with review, never silent overwrite):

Field updates: MAX(updated_at) wins; loser marked conflict and surfaced in FO ("Order LND-104 changed by Manager — Review") + Admin log.
Payments: never auto-merged — duplicate idempotency_key dedupes; amount mismatches go to failed + Admin reconcile queue (money-safety over convenience, extends enhance.md §15).
Status transitions validated server-side (Received→…→Collected); illegal jumps rejected with reason shown at counter.

1. Decision 4 explained: What packages/ actually means
What I proposed:


Gabfix-ERP/
  admin-dashboard/
  gabfix-laundry-front-office/
  gabfix-inhouse-erp/
  packages/
    theme/
    ui-kit/
    api-client/

What this does NOT mean:

The three apps depend on each other at runtime, or need a shared server to render, or can't be deployed separately.

What it DOES mean:

The three apps share source code at build time, but each produces a fully self-contained deployment artifact at deploy time.

Here is the mechanism:

packages/theme and packages/ui-kit are source libraries, not running services. They contain .css, .tsx, .ts files only.
Each app declares them in its own package.json as file:../packages/theme dependencies.
When you run npm run build in gabfix-laundry-front-office/, Vite bundles copies of the theme CSS + components it actually uses into that app's own dist/ folder.
That dist/ folder is then deployed independently - e.g.:
admin.gabfix.com <- admin-dashboard/dist
counter.gabfix.com or tablet kiosk <- gabfix-laundry-front-office/dist
field.gabfix.com <- gabfix-inhouse-erp/dist
At runtime, there is zero cross-app import. If you shut down Admin, Laundry and Inhouse keep running. If you delete admin-dashboard/, the other two still build.
So: shared repository for storage + shared source for consistency, self-contained for deployment. This satisfies your requirement.

4. Laundry PWA: online-first or offline-first? Guidance
You asked which direction updates should flow. There are two valid patterns - here is the guidance:

Option 1: Online-first (try network, fall back to local)
Every save tries POST /api/... first.
If network fails, save to Dexie and queue.
Pros: server numbers (LND-104, RCPT-201 from enhance.md §8 sequences) are immediate when online; less reconciliation logic.
Cons: every network hiccup becomes a spinner / error at the counter. Staff learn "click twice when slow" → duplicates. During an outage the app feels broken even though it technically has a fallback. For a front counter with walk-in customers, this is the wrong feel.
Option 2: Offline-first / local-first (my recommendation for the counter)
Every save writes to Dexie first, UI confirms instantly (<50ms), then sync pushes to server in background.
When online: push happens in ~1s, server ACK returns real number + PDF URL, DRAFT ticket auto-upgrades.
When offline: rows stay pending, header shows ○ Offline — 3 waiting, counter keeps serving.
Pros: counter never stops. Matches Dashboard guidelines §5 (freshness is honest: "Last synced 14:32") and erp_design.md empty/loading states (skeleton + retry, never dead page).
Cons: requires temp-ID + idempotency design (already in the addendum §4: local-<uuid> + idempotency_key, numbers assigned server-side at push, DRAFT → authoritative reprint). This is ~2-3 days extra in Phase 1, already costed.
Recommendation: offline-first for Laundry, online-first for the other two apps.

Rationale:

Laundry counter = queue of impatient humans + often a single shared tablet on shop WiFi. Downtime cost is immediate (lost sale, handwritten tickets that never enter the system).
Admin = back office with stable internet; needs live ledger truth, so online-first + SSE is correct.
Inhouse = field with intermittent signal, but jobs are multi-hour; a small outbox for pings + status changes is enough (already in enhance.md §14 beacon design). Full offline job editing is Phase 6+ scope creep - do not add it now.
Money-safety note (extends enhance.md §15): offline payments are never auto-merged. Same idempotency_key dedupes retries; amount mismatches quarantine to Admin reconcile. This is why offline-first is safe for cash/MoMo at the counter.

5. Dexie pruning: does it fetch deeper history from online?
Yes - exactly. Pruning is local eviction, not server deletion. Clarified:

Server is the permanent record. PostgreSQL keeps everything (subject to GPS_RETENTION_DAYS only for raw pings; orders/payments never auto-delete).
Dexie is a working window. Keep: all open orders + last ~90 days synced/closed + ~500 recent customers + lookups. This keeps a low-end tablet fast (IndexedDB slows past ~10-20k rows with indexes).
Pruning = delete local copies of rows that are synced AND collected AND older than 30 days. Pending/conflict/failed rows are never pruned.
Deeper history is fetched on demand:
Counter search for an old receipt → cache miss → GET /api/laundry?query=... (scoped, paginated per enhance.md §9) → result cached back into Dexie.
GET /api/sync/pull?since= re-seeds anything evicted if needed (e.g., after reinstall, bounded 90-day seed pull).
So the tablet feels infinite while storing finite.
Think of it as: server = library, Dexie = desk. You keep today's files on the desk, archive finished ones back to the library, and fetch any old file in seconds when a customer asks.

Prune threshold: synced + collected + >30 days.
Customer cache: last-500-used at this branch.
Seed pull on fresh login: this branch, 90 days + all open.
